### 核心组件

| 组件 | 类名 | 职责 |
|---|---|---|
| 协议解析器 | `THSProtocolParser` | TCP 字节流 → 帧 → JSON/二进制 |
| 数据提取器 | `L2DataExtractor` | 帧 → Tick/Quote/tb10 |
| Redis 写入器 | `RedisWriter` | 批量缓冲 + Pipeline 写入 |
| 股票池 | `StockPool` | Redis Set 管理 |

### 数据流

```
TCP 字节流
   │
   ▼
parser.feed(bytes)       ← 喂入原始字节
   │
   ▼
parser.parse_frames()    ← 按 Magic(0xFDFDFDFD) 切帧
   │
   ▼
for frame in frames:
   ├── extractor.extract_ticks()    → tick → tick_batch
   ├── extractor.extract_quote()    → quote → quote_batch
   ├── extractor.parse_tb10()       → tb10 → quote_batch
   └── frame["json"]["events"]      → events → redis.xadd
   │
   ▼
writer.flush_all()       ← Pipeline 批量写入 Redis
```

## 3. Redis 数据结构

| Key 模式 | 类型 | 用途 | 消费端读取方式 |
|---|---|---|---|
| `ths:l2:meta` | Hash | 元数据/统计 | `HGETALL` |
| `ths:l2:pool` | Set | 股票池 | `SMEMBERS` |
| `ths:l2:events` | Stream | 系统事件 | `XREAD` |
| `ths:l2:tick:{code}` | Stream | 逐笔成交 | `XREAD` / Consumer Group |
| `ths:l2:quote:{code}` | Hash | 价格快照 | `HGETALL` |

## 4. 容量评估

### 当前配置下的上限

| 维度 | 评估 | 结论 |
|---|---|---|
| Redis 写入 | Pipeline 批量，本地连接，10万+ ops/s | ✅ 可撑 1000+ 股票 |
| asyncio 事件循环 | I/O 密集型，单线程可撑数千连接 | ✅ 无压力 |
| 解析 CPU (Python) | struct.unpack + JSON，约 5-10 万帧/s | ⚠️ 1000 支 × 100帧/s = 10万 → 接近上限 |
| 服务器端 | 单连接推送所有订阅股票 | ✅ 500-1000 只没问题 |
| 内存 | 帧缓冲 + 批量队列 | ✅ 几十 MB |

### 延迟分析

| 环节 | 当前延迟 | 说明 |
|---|---|---|
| TCP 接收 | < 1ms | 网络传输 |
| 解析 | < 1ms/帧 | struct.unpack + JSON |
| 批量缓冲 | 0-1000ms | 取决于 flush 频率 |
| Redis 写入 | < 1ms | Pipeline 本地连接 |
| **端到端** | **< 1000ms** | **当前秒级** |

### 股票数量 vs 延迟

| 股票数 | 帧率 (估计) | CPU 使用率 | 延迟 |
|---|---|---|---|
| 5-50 | 10-100 fps | < 10% | < 100ms |
| 50-200 | 100-500 fps | 10-30% | < 200ms |
| 200-500 | 500-2000 fps | 30-60% | < 500ms |
| 500-1000 | 2000-5000 fps | 60-100% | < 1000ms |
| 1000+ | 5000+ fps | 100%+ ❌ | 需要优化 |

## 5. 瓶颈分析

### 瓶颈 1: 解析 CPU (Python 单核)

```
问题: 每帧都要 struct.unpack + JSON 解析 + 正则匹配
      极端行情时帧率可能是平时 10 倍

影响: 1000+ 股票时 CPU 100%，延迟增大

解决: 多进程解析 / C 扩展解析器
```

### 瓶颈 2: 单 TCP 连接

```
问题: 断了就全断，虽然有自动重连但会丢数据
      单连接无法利用多核

影响: 可靠性风险

解决: 多 TCP 连接分摊股票
```

### 瓶颈 3: 批量写入频率

```
问题: flush_all() 每 1 秒才写一次
      消费端要毫秒级延迟时需要更频繁

影响: 延迟受限于 flush 频率

解决: 实时写入 / 更短 flush 间隔 / 写入合并
```

## 6. 未来优化方向

### Phase 1: 毫秒级延迟 (5ms 写入)

| 优化 | 改动 | 效果 |
|---|---|---|
| 实时写入 | 去掉 batch，每帧直接 Pipeline 写入 | 延迟 < 5ms |
| Pipeline 优化 | 每 10ms 或每 100 帧 flush 一次 | 平衡吞吐和延迟 |
| 写入合并 | 同一股票 100ms 内多次 tb10 只写最后一次 | 减少无效写入 |

### Phase 2: 高并发 (1000+ 股票)

| 优化 | 改动 | 效果 |
|---|---|---|
| 多 TCP 连接 | 2-3 路连接分摊股票 | 提高采集带宽 |
| 多进程解析 | 解析和写入分离到不同进程 | 利用多核 CPU |
| 消息队列 | 采集 → ZeroMQ → 解析 → Redis | 解耦生产消费 |

### Phase 3: 高可用

| 优化 | 改动 | 效果 |
|---|---|---|
| 主备连接 | 双 TCP 连接热备 | 零丢数据 |
| Redis 主从 | 主从复制 + Sentinel | 高可用 |
| 断点续传 | 记录最后帧序号 | 重连后补数据 |
