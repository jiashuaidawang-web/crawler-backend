# 踩坑记录 2026-08-14

日批编排器(Pipeline)Phase 1 实施中的设计与实现陷阱。

## 问题现象

设计"上游总数真值校验"时的几个关键未知/误判,若不做实测会把方案建立在错误假设上。

## 根因(按影响排序)

### Bug 1(设计事实):`crawl_task` 表没有 `trade_date` 列

完成探测不能 `WHERE trade_date=?`,日期编码在 `unique_key` 里(格式 `taskType|source|date[*pn]`)。
→ 必须按 `task_type IN (...) AND unique_key LIKE 'TYPE|source|date%'` 聚合 `status IN ('PENDING','RETRY')`。
→ `CrawlTaskMapper` 新增 `countByStatusLike(like)`。

### Bug 2(设计事实):上游总数字段在 B 类阶段"不存在"是误判

最初以为 NORTHBOUND/INDEX_DAILY/DRAGON_TIGER 没有上游 total。**实测发现都有**:
- datacenter(龙虎榜):`result.count`(pageSize=1 时仍返真值,可做轻量探测)
- clist:`data.total` + `data.diff.size()`
- pool:`data.tc`
- kamt(北向):`data.s2n` 数组 size(= 分钟级数,每日 241)

→ 每个阶段的总数都直接来自上游响应本身,口径统一。**不能假设,要实测。**

### Bug 3(编译陷阱):persistence 实体命名覆盖 admin 枚举

新建 `persistence.entity.PipelineStage` 把 `admin.pipeline.PipelineStage` 枚举覆盖,
orchestrator 里 `entity.getPolicy()`/`entity.name()` 全报"找不到符号"。
→ 实体重命名为 `PipelineStageRecord`,明确区分"DB 记录"和"枚举定义"。

### Bug 4(运行时陷阱):`PipelineMapper` 用 `@Mapper` 不被扫描

项目注释明示"双数据源下不加 @MapperScan",现有 mappers 全部显式 `MapperFactoryBean`。
`@Mapper` 注解的 mapper 根本不被注册 → 启动注入失败。
→ 删 `@Mapper`,改显式 Bean:`DataSourceConfig` 加 `pipelineMapper(..., pgSqlSessionFactory)`。

### Bug 5(运行时陷阱):`insertStage` / `insertRun` 拿不到自动生成的 id

openGauss 的 `INSERT ... RETURNING` 在 MyBatis 里不能直接当返回值拿到(尤其带 `WHERE NOT EXISTS`)。
`entity.getStageId()` 为 null → `updateStage` 写 NULL。
→ `insertStage` 加 `@SelectKey(statement="SELECT currval('pipeline_stage_stage_id_seq')", keyProperty="s.stageId", before=false)`;
`insertRun` 改两步:`insertRunIgnoreConflict` + `selectRunIdByDate`。

### Bug 6(逻辑陷阱):查 CK 重复时自然键含不存在的列

`DedupService.REGISTRY` 的自然键含 `data_source`,但该列在 CK 表/行里实际不存在
(正是 memory-dedup N→0 bug 的根因)。若直接按自然键 GROUP BY,`data_source` 全 null → 误判。
→ 查重复前先查 `system.columns` 得表实际列,只取自然键中真正存在的列,且用 `toString(coalesce(col,''))` null 安全拼接。

- 无线上修复(纯新增)。

## 关键排查经验

1. **"有没有总数字段"不能看代码猜,要实测**:写临时脚本调接口看响应 envelope,比读解析器更准(解析器可能只读 data 没读 result 层)。
2. **命名空间要警惕**:同项目里 persistence 实体和 admin 枚举同名会静默覆盖,编译错但不直观。实体加 `Record` 后缀是低成本避坑。
3. **MyBatis mapper 注册方式要统一**:混用 `@Mapper` 显式 Bean 会漏注册,看项目现有风格(本工程全显式 `MapperFactoryBean`)。
4. **openGauss 拿 generated id 用 `@SelectKey` + `currval`**:`RETURNING` 在 MyBatis 复杂 SQL 里不可靠。
5. **自然键 ≠ 表实际列**:REGISTRY 的自然键是"语义键",可能含内存去重用的虚拟列(如 data_source),查 CK 前必须和实际列取交集。

### Bug 7(逻辑 bug):inserted=0 导致 expectedTotal=0,校验被跳过(假 DONE)

编排器首次跑 2026-08-13 STOCK_DAILY,日志显示:
```
[seedStockDailyPages] date=2026-08-13 total=5549 pageSize=100 pages=56 inserted=0
```
seed 探测到上游 total=5549、应发 56 任务,但 inserted=0(任务已存在,幂等跳过)。
StageSeeder 用 `inserted*100` 算 expectedTotal → 0 → TotalCountCountValidator 跳过 → 阶段空 DONE。
**这是假成功:什么都没校验就过了。**

→ 改 `seedStockDailyPagesResult` 返回 `SeedResult`,把上游真实 total=5549 放在 `expectedTotal`,
不依赖 inserted 推算。StageSeeder 直接用 `seedResult.expectedTotal()`。
原 `seedStockDailyPages` 保留返回 int(内部调 `.inserted()`),`dailySeed`/JobController 调用方零改动。

### Bug 8(严重运行时事故):worker 无熔断器 + maxProxyFetchAttempts=-1 → 代理池失效时无限烧 IP,零数据入库

**问题现象**
2026-08-14 另一台机器 admin+worker 空转约 6.7 小时(13:07 起),烧掉约 **5000 个代理 IP**,但 **ClickHouse 行情数据零入库**。
- worker 侧:`fetchWithWorkerProxy success`=0、`fetch ok`=0、`complete ok`=0;82 个任务认领、81 个失败、81 次 give up(每任务烧满 10 IP);worker 侧 407 共 **819 次**。
- admin 侧:15:30:44 熔断器触发(连续 35 次失败)后停止;唯一入库的是 PostgreSQL 里 15:51 写入的 **1102 条 seed 任务行**(不是行情数据)。
- 行情数据(`DedupWriter.write`)从未执行,因为 `strategy.fetch(ctx)` 每次都抛异常。

**根因(按影响排序)**

1. **触发事件**:代理供应商 `QgLongTermProxyProvider`(用户 `8XMUHNWJ`)的凭据在 15:29:59 突然失效,所有 IP 统统返回 **HTTP 407 代理认证失败**。
2. **缺陷 A(主因)**:`WorkerProxyManager`(crawler-strategy) **没有熔断器**——而 admin 的 `ProxyManager` 有完整熔断器(连续 35 次失败即停)。两者是独立组件,admin 停了 worker 还在跑。
3. **缺陷 B(兜底缺失)**:`StrategyFactoryConfig.java:43` 把 worker 配成 `new WorkerProxyManager(provider::acquire, -1)`,`-1` = 无限制。admin 的 `CIRCUIT_BREAKER_THRESHOLD` 在 worker 侧完全没有对应。
4. **缺陷 C(差一放大)**:`EastmoneyApiStrategy.java:211` 条件是 `used < MAX_PROXY_FETCH_ATTEMPTS_PER_TASK - 1`(即 `used < 9`),第 9 次就放弃;失败直接走 worker RETRY,同一任务反复进队列,每个任务烧的 IP 不止 10 个(81 任务烧 738 IP)。

**修复**(3 处,最小改动对齐 admin 现有风格)

1. `crawler-strategy/.../eastmoney/WorkerProxyManager.java` —— 加完整熔断器:
   - 新增 `consecutiveFailures`(AtomicInteger)、`circuitBreakerOpen`、`circuitBreakerOpenTime`。
   - 常量 `CIRCUIT_BREAKER_THRESHOLD=50`、`CIRCUIT_BREAKER_RESET_MS=10min`(比 admin 的 30min 短,worker 恢复应更快)。
   - `getProxy()` 开头加熔断器检查:开启中返回 null(不提取新 IP,`EastmoneyClient.get` 对 proxy=null 安全,走无代理 BASE_CLIENT 快速失败不烧 IP);超 10min 后半开。
   - `invalidate()` 累加连续失败 + `checkCircuitBreaker()`;**熔断器开启后 `invalidate()` 不再重复计数**(避免任务级重试 10 次 + 管理器级 50 次叠加成几百次浪费)。
   - 超限(`fetchAttemptCount >= maxProxyFetchAttempts`)也触发熔断检查。
   - 新增 `getCircuitBreakerStatus()` / `resetCircuitBreaker()`,对齐 admin 的 `ProxyManager`。
2. `crawler-worker/.../config/StrategyFactoryConfig.java:43` —— 把 `-1` 改成 `50`(有限值,与任务级 10 次配合,多任务共享留缓冲)。
3. `crawler-strategy/.../eastmoney/EastmoneyApiStrategy.java:211` —— 差一修正:`used < MAX_PROXY_FETCH_ATTEMPTS_PER_TASK - 1` → `used < MAX_PROXY_FETCH_ATTEMPTS_PER_TASK`,让 10 个 IP 全部可用。

**验证**
- `mvn -pl crawler-worker -am compile` 通过。
- 熔断器开启后 `getProxy()` 返回 null → `client.get(url, ua, null)` 走 `BASE_CLIENT`(无代理)→ 快速失败,**不浪费 IP**。

**关键排查经验**
1. **admin 与 worker 的熔断器是独立组件**:admin 停了不代表 worker 停。任何一级有"取新 IP 重试"的组件,都必须自带熔断器,不能依赖上游组件兜底。
2. **`-1` 无限制是代理/IP 类组件的高风险配置**:凡是带"获取外部资源(代理/IP/配额)"循环的组件,默认值必须是有限值,熔断器是必须不是可选。
3. **差一错误在重试逻辑里会被 RETRY 放大**:任务级"少用 1 个 IP 就放弃"看似节约,实际让任务反复入队、总消耗反而更大。
4. **日志里 `success=0` + `give up=N` + `熔断器触发` 三者同时出现 = 代理池整体失效的典型签名**,应直接触发告警(目前 worker 侧熔断触发有 ERROR 日志,可作为告警信号)。
