# 踩坑记录 2026-08-13

龙虎榜主表 `dragon_tiger` 数据丢失排查与修复全过程。

## 问题现象

- 当天龙虎榜实际 **71 家**，数据库 `count(*)` 只有 **67 条**。
- 触发接口：`POST /api/crawl/seed-dragon-tiger {"tradeDate":"2026-08-13","source":1}`。
- worker 日志：API 返回 87 行 → 批内去重 83 行 → 写入成功，但 `VOLUME_DEVIATION expected=1 actual=87`。

## 根因（三个独立 bug，按影响排序）

### Bug 1（真·数据丢失）：线上表 `ORDER BY` 缺 `reason`

线上 `dragon_tiger` 实际 DDL：

```sql
ENGINE = ReplacingMergeTree(_ver) ... ORDER BY (ts_code, trade_date)  -- 缺 reason！
```

而代码去重键 / 主 schema `clickhouse-schema.sql` 是 `(ts_code, trade_date, reason)`。

**后果**：同一只股票同一天因多个原因上榜（如同时触"日涨幅偏离值 7%"和"日换手率 20%"）→ 多行共享 `(ts_code, trade_date)` → `ReplacingMergeTree` 静默折叠成一行。71 家变 67，丢了 4 行的上榜原因。**不是显示问题，是实打实的数据丢失。**

`count()` 和 `count() ... FINAL` 都是 67，说明 part 已充分合并，丢失的行在现有数据里没有副本，无法从表中恢复——只能重灌。

### Bug 2（真·逻辑 bug）：`DedupService.dedupInBatch` 按整行去重

`DedupService.java:482` 定义的自然键是 `(ts_code, trade_date, reason)`，但实现是 `reversed.add(r)` —— 按整行 `Map.equals()` 全 43 列去重。

- 结果：87 → 只去掉 4 行**整行完全相同**的，同键不同净额的行全保留 → 写入了 83 行而非 ~71 行。
- 附带问题：`keyOf` 遇 null 键列就 `return null`，然后整行丢弃；龙虎榜 `reason` 是 Nullable，**reason 为空的行会被丢弃**。

### Bug 3（噪音）：`seedDragonTiger` 硬编码 `expectedCount=1`

`SeedGenerator.java:418` 的 `buildTask("DRAGON_TIGER", ..., 1)`。目录 `TaskTypeCatalog` 规定 DRAGON_TIGER 是 `marketWide`、`defaultExpected=null`（不做量校验）。结果每次龙虎榜都误报 `VOLUME_DEVIATION 8600%`，但 `validate()` 只记 `crawl_alert` 不阻塞写入——纯噪音。同 bug 在 `seedDragonTigerDetails`(1098) 和 `chainDragonTigerDetails`(1132)。

## 修复

### 代码修复（3 处，待部署）

1. **`DedupService.dedupInBatch`**：改为按 `keyOf()` 自然键字符串去重（`LinkedHashMap<String, T>`，保留末位）；`keyOf` 遇 null 用 `\0` 占位参与去重，不丢行。
2. **`SeedGenerator`**：三处 `expectedCount=1` 改 `null`，与目录一致。
3. **`dragon_tiger_rebuild.sql`**：`ORDER BY (ts_code, trade_date)` 补上 `reason` → `(ts_code, trade_date, reason)`，与主 schema 对齐。

### 线上修复（已执行）

1. **表迁移**：因 ClickHouse 23.8 的 `MODIFY ORDER BY` 不能追加列（报 `BAD_ARGUMENTS`），改用安全迁移——建新表 → `RENAME` 原子切换 → `INSERT...SELECT` 拷数据 → 验证 174 行零丢。新表 `ORDER BY (ts_code, trade_date, reason)` + `allow_nullable_key=1`。
2. **重灌 08-13**：通过重置 `crawl_task` 中任务 19345 为 PENDING 让 worker 重新抓取（效果等同调 seed 接口）。重灌后 `distinct ts_code = 71` ✓。

## 关键排查经验

1. **ClickHouse `ReplacingMergeTree` 的数据丢失**：`count(*)` 和 `count() ... FINAL` 一致 ≠ 数据完整。若 `ORDER BY` 键比真实语义键粗，折叠掉的行在表里**没有残留副本**，不可恢复。
2. **ClickHouse 23.8 `MODIFY ORDER BY` 限制**：不能给已有排序键追加列，只能改表达式里用"新增列"。要改排序键只能重建表。
3. **线上表 vs schema 文件不一致**：`clickhouse-schema.sql` 是 `(ts_code, trade_date, reason)`，但 `dragon_tiger_rebuild.sql` 是 `(ts_code, trade_date)`，线上表实际按 rebuild 脚本重建。**多个 schema 文件之间要一致**。
4. **验证去重是否错杀**：去重后查 `GROUP BY 自然键 HAVING count()>1`（空=安全），并对比已知的合理家数。
5. **`ReplacingMergeTree` 列不可为 Nullable（默认）**：排序键含 Nullable 列需 `SETTINGS allow_nullable_key=1`，否则 `CREATE TABLE` 报 `ILLEGAL_COLUMN`。

# 2026-08-13（续）— 池子/主力资金流数据丢失排查

## 问题现象

- 5 个池子（涨停/跌停/炸板/强势/次新）跑批成功，`seed-pools-only` 返回 `inserted>0`，但库里当天数据为空。
- 同样，`main_fund_flow` 也没数据。

## 根因（按影响排序）

### Bug 1（最大影响）：批内去重键含 `data_source`，row 里没有 → 整批丢光

提交 `92b49c7 修改索引` 给 `DedupWriter.DEDUP_KEYS`（`DedupWriter.java:355-380`）的去重键加了 `data_source`：

```java
k("STOCK_DAILY", "ts_code", "trade_date", "data_source");  // ← 加了 data_source
k("LIMIT_UP",     "ts_code", "trade_date", "data_source");
k("STRONG_POOL",  "ts_code", "trade_date", "data_source");
...等等
```

但东财解析器 `EastmoneyParsers` **从不把 `data_source` 放进 row**——`data_source` 是写入时由 `source` 参数注入的（`setPoolBaseFields` 第 231/316 行）。

`DedupService.keyOf`（`DedupService.java:499`）遇 null 键列就 `return null`，然后 `dedupInBatch` 第 490 行 `if (key != null)` 才保留 → **整批被丢弃**。

日志铁证：
```
[DedupWriter] 批内去重 taskType=STRONG_POOL, 100 -> 0 行
[DedupWriter] 批内去重 taskType=CIXIN_POOL,   47 -> 0 行
[DedupWriter] 批内去重 taskType=LIMIT_UP,      59 -> 0 行
```

对比：`DRAGON_TIGER`（去重键 `ts_code, trade_date, reason`，**不含 data_source**）→ `87 -> 83` 正常工作。

**受影响任务类型**（去重键含 `data_source` 的）：STOCK_DAILY、STOCK_DAILY_HISTORY、STOCK_WEEKLY、LIMIT_UP、LIMIT_DOWN、LIMIT_ZHABAN、STRONG_POOL、CIXIN_POOL、MAIN_FUND_STOCK、MAIN_FUND_BOARD、STOCK_BY_BOARD。

### Bug 2：`seed-pools-only` 返回 `inserted=0` 不代表失败——任务已存在就不重建

`SeedGenerator.seedPoolTasksSingle` 用 `mapper.insertIfAbsent`（按 `unique_key` 幂等）。`unique_key = taskType|source|date|pn` 是确定性的，所以**重复下发同一日期不会重建任务**。

如果旧任务已 COMPLETE 但当时数据为空（如盘前跑、东财 tc=0 下了兜底 task），再跑 `seed-pools-only` 全部 `inserted=0`，不会重新抓取。需手动 `DELETE FROM crawl_task` 清掉旧任务再重发。

### Bug 3：`/api/crawl/seed` 未传 `uniqueKey` → null 违反 NOT NULL 约束

`SeedController.seed`（第 58 行）直接 `task.setUniqueKey(req.uniqueKey())`。调用方不传就 null → `insertIfAbsent` 报 `null value in column "unique_key" violates not-null constraint`，返回 500。

### Bug 4：`MAIN_FUND_FLOW` 不是 worker 认识的任务类型

`EastmoneyEndpoints.get` 只认 `MAIN_FUND_STOCK` 和 `MAIN_FUND_BOARD`（端点已实现）。`seed` 接口把 `MAIN_FUND_FLOW` 当普通单任务下发 → worker 找不到端点 → `UnsupportedOperationException: Eastmoney endpoint NOT implemented for taskType=MAIN_FUND_FLOW TODO M2`。

正确做法：`MAIN_FUND_FLOW` 要拆成 STOCK + BOARD 两个子任务（跟 `STOCK_DAILY` 分页拆法同模式）。

## 修复

### 代码修复

1. **`DedupWriter.DEDUP_KEYS`**（`DedupWriter.java:357-377`）：去掉去重键里的 `data_source`。批内去重它是常量且不在 row 里；跨源去重由 CK `ReplacingMergeTree` / DB 唯一键保证（`DedupService.REGISTRY` 保留不动）。**worker 容器已 rebuild + restart 生效。**
2. **`SeedController.seed`**：`uniqueKey` 未传时自动生成 `taskType|source|date`。
3. **`SeedController.seed`**：加 `MAIN_FUND_FLOW` 特殊处理 → 拆成 `seedMainFundStock` + `seedMainFundBoard`。

### 线上/运维修复

1. **worker 容器重建**：`docker-compose build crawler-worker && docker-compose up -d crawler-worker`（让去重键修复生效）。
2. **admin 容器待重建**：uniqueKey 生成 + MAIN_FUND_FLOW 拆分在 admin，改完需 rebuild admin。
3. **清旧任务再重发**（让 worker 重新抓）：
   ```sql
   DELETE FROM crawl_task WHERE task_type IN ('MAIN_FUND_STOCK','MAIN_FUND_BOARD') AND unique_key LIKE '%2026-08-13%';
   ```

## 关键排查经验

1. **"跑批执行了"≠"数据落库了"**：`seed-xxx` 返回的 `inserted` 是**下发的任务数**，不是数据行数。要确认 worker 真正消费并写入。
2. **批内去重日志 `N -> 0` 是红灯**：去重后行数变 0，说明去重键和 row 字段不匹配（键列在 row 里为 null）。健康去重是 `N -> M`（M 接近 N）或无日志。
3. **`data_source` 在批内去重键里是错的**：同一批的 source 相同，它起不到去重作用；row 里又没有这个字段，只会导致丢行。
4. **改源码必须 rebuild + restart 对应容器**：admin 和 worker 是独立 Docker 容器，改源文件不重启＝白改。每次修完要确认容器跑的是新代码。
5. **重发前先清旧任务**：`insertIfAbsent` 幂等，旧任务（即使 COMPLETE/FAILED）会挡住新任务重建。
6. **对比法找去重 bug**：同日志里找不含 `data_source` 的任务类型（如 DRAGON_TIGER `87->83`）作对照，快速定位是 `data_source` 的问题。
7. **`MAIN_FUND_FLOW` 是虚拟类型**：worker 只认 `MAIN_FUND_STOCK`/`MAIN_FUND_BOARD`，下发前必须拆分。
