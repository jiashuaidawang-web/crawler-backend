# 踩坑记录 2026-09-26

## 问题：青果代理全线 407 "Failed to authenticate with proxy"，熔断器反复开启

### 现象

- 所有 `STOCK_KLINE_MINUTE` 任务失败，日志三连：`WorkerProxyManager` 熔断 → `Failed to authenticate with proxy` → `task -> FAILED (retryCount=3/3)`
- 换任何 IP 都是同样错误，~100ms 内快速失败（代理可达、是主动拒绝，不是网络不通）
- 熔断 10 分钟后半开恢复，拿到新 IP 依旧 407，连续失败重新累积 → 熔断循环

### 根因（按影响排序）

1. **直接触发：青果控制台 IP 白名单被清空。**
   本项目的代理认证一直走的是「IP 白名单」而不是帐密——代理 URL 里的 `user:pass` **从来没被发送到代理**（见根因 2），白名单是唯一实际生效的认证手段。白名单清空 → 每个 CONNECT 请求都被 407 拒绝。

2. **隐藏代码 bug：`EastmoneyClient.java:144` 用 `builder.authenticator()` 注册 407 凭证处理器，但那是「源站 401」认证器；代理 407 认证必须用 `builder.proxyAuthenticator()`。**
   OkHttp 4.12.0 对 HTTPS-over-HTTP-proxy 的 CONNECT 隧道请求只带 `Host`/`Proxy-Connection`/`User-Agent` 三个头（源码 `RealConnection.kt` 的 `createTunnelRequest()`），预发与重试凭证只走 `proxyAuthenticator`。全仓库历史上从未用过 `proxyAuthenticator`（`git log --all -S "proxyAuthenticator"` 为空）→ 帐密从未发出。**之前「青果代理稳定的很」的时期，全是白名单在放行。**

3. **本轮无效修复尝试（未部署，且部署了也没用）：**
   - 主动加 `Proxy-Authorization` 请求头（`EastmoneyClient.get()` 未提交改动）：该头只会随隧道内的请求发给东财，**不会出现在 CONNECT 请求上**，对代理认证无效。OkHttp 源码注释明说 tunnel 只带最少头。
   - 用户名 `businessId` → `authKey`（`QgLongTermProxyProvider.java` 未提交改动）：凭证根本没发出去，换用户名无从生效；且运行中的 worker 是 HEAD 代码（堆栈 `EastmoneyClient.java:64` 与 HEAD 行号一致，工作区改动该行在 74；日志用户名 `7pabvimp`=business-id，而 auth-key=`NM8XFDR2`）。

### 证据链

- OkHttp 4.12.0 源码（`~/.m2/repository/com/squareup/okhttp3/okhttp/4.12.0/okhttp-4.12.0-sources.jar` → `RealConnection.kt`）：
  - `createTunnelRequest()`：CONNECT 只有 Host/Proxy-Connection/User-Agent；预发认证靠 `proxyAuthenticator` 对一个 fake 407 响应返回带凭证的请求
  - `createTunnel()`：407 时 `route.address.proxyAuthenticator.authenticate(...) ?: throw IOException("Failed to authenticate with proxy")` —— 堆栈里的 `RealConnection.kt:476` 正是这一行
  - `builder.authenticator()` = 源站 401；`builder.proxyAuthenticator()` = 代理 407
- `git log --all -S "proxyAuthenticator"` 全仓库无结果
- **2026-08-14 事故重新解读**：当时记录为「凭据突然失效，所有 IP 统统 407」，但凭证从未发出过 → 那次 407 风暴实际也是白名单/出口 IP 变化类问题（如公网 IP 变了、供应商侧白名单变动），不是帐密过期。

### 修复（二选一）

**方案 A（最快，零代码）：青果控制台把 worker 服务器的公网 IP 加回白名单** → 恢复到之前的可用状态。状态：不采用（每天跑批前手动加白名单太麻烦，决定切帐密）

**方案 B（真正切到帐密认证）——已实测验证可行（2026-09-26 21:30~21:52，curl 实测）：**
1. `EastmoneyClient.java:144`：`builder.authenticator(` → `builder.proxyAuthenticator(`（只改这一处，OkHttp 会在第一个 CONNECT 上预发凭证，无额外往返）
2. 回滚 `get()` 里主动加 `Proxy-Authorization` 头的无效改动
3. 用户名用 authKey（实测确认，见下）
4. 处理 `@Component` 与 `SeedStrategyBeans @Bean` 的同名冲突（见下）

**实测结论（curl 直连代理隧道）：**
| 测试 | 结果 |
|------|------|
| 无凭证 CONNECT | 407（白名单确实空了） |
| `NM8XFDR2:22574E11640D`（authKey 作用户名） | ✅ 200 隧道建立，东财返回真实分时数据 |
| `7pabvimp:...`（businessId 作用户名） | 407（businessId 不是认证用户名） |
| 错误密码 | 407（密码确实被校验） |
| 407 响应头 | 带 `Proxy-Authenticate: Basic realm=""`（OkHttp/Chromium 挑战-应答均可自动完成） |

关键推论：**帐密模式在青果侧已开启、且不绑定出口 IP**（测试机不在任何白名单也能通过认证），无需再去青果后台做任何操作。

### 方案 B 实施记录（2026-09-26 已完成 + 端到端验证通过）

代码改动（5 个文件）：
1. `EastmoneyClient.java`：
   - **核心修复**：`builder.authenticator(` → `builder.proxyAuthenticator(`（407 由代理返回，必须用 proxyAuthenticator；OkHttp 会在第一个 CONNECT 预发凭证，无额外往返）

   - 新增 `maskProxy()` 日志脱敏
2. `QgLongTermProxyProvider.java`：保留 authKey 作用户名（实测验证正确）+ acquire 日志脱敏
3. `WorkerProxyManager.java` / `EastmoneyApiStrategy.java`：代理日志脱敏
4. `TradingDayChecker.java`（admin）：**去直连**，改走 `ProxyManager.executeWithRetry`（青果代理 + 自动换 IP + 熔断），删除 `(date, proxyStr)` 重载

### 补充验证：纯 HTTP（非 HTTPS）URL 在帐密模式下不受影响（2026-09-26 22:25）

背景：`SeedGenerator` 的东财 URL 有意用 `http://`（`SeedGenerator.java:1072` 注释：避开当时 CONNECT 隧道加不上凭证的 407 bug；且 HTTPS 的 TLS 指纹对爬虫识别更敏感）。切帐密后需确认纯 HTTP 路径依然可用。

三层实测（全过）：

| 层 | 验证方式 | 结果 |
|----|----------|------|
| 青果代理 | curl：纯 HTTP 无凭证 → 407；带帐密 → 200+数据 | ✅ 青果对纯 HTTP **同样做 407 认证**（不只管 CONNECT） |
| OkHttp 源码 | `RetryAndFollowUpInterceptor.kt:215`：任何 407 都调 `client.proxyAuthenticator.authenticate()` | ✅ proxyAuthenticator 同时覆盖 CONNECT 隧道与纯 HTTP 两种模式 |
| 生产代码 | `EastmoneyClient` + `http://push2his...` + 帐密代理 | ✅ rc=0 真实 K 线 |

机制差异（过 HTTP 代理时）：
- **HTTPS**：认证发生在 CONNECT 隧道建立时，OkHttp 预发凭证，无额外往返
- **纯 HTTP**：无 CONNECT，请求以完整 URL 直接发给代理 → 407 → proxyAuthenticator 应答重发。**每条新连接多一次 407 往返**，连接池复用后可忽略
- 两种模式下 `Proxy-Authorization` 均为逐跳头（hop-by-hop），代理消费后不转发，东财看不到凭证

结论：**HTTP / HTTPS 都正常，无需改任何 URL**。`SeedGenerator.java:1072` 注释的历史理由（CONNECT 407 bug）已随本次修复过时，但保留 HTTP 的选择依然成立（规避 TLS 指纹识别——注意过 HTTP 代理并不能隐藏 TLS 指纹，TLS 是端到端的）。

### 后续清理（无论选哪个方案）

- **熔断器重置**：监控页面手动重置（`resetCircuitBreaker`）或重启 worker，否则要等 10 分钟半开自愈
- **本次 FAILED(3/3) 的任务是终态**（如 17925/17926/17927），worker 不会再认领：pipeline `force=true` 重跑（内部会 `forceResetDeadTasks`）或手动把任务重置为 PENDING，否则这几天的分时数据有缺口

### 关键排查经验

- **OkHttp 代理认证只有一条路：`proxyAuthenticator()`。** `authenticator()` 是给源站 401 的；CONNECT 隧道请求不携带原请求的任何头，请求级 `Proxy-Authorization` 头对 HTTPS 代理认证无效。
- **「代理 URL 里带 user:pass」在 `java.net.Proxy` + OkHttp 组合下是摆设**：凭证只可能通过 authenticator 发出，URL 里的帐密不会被自动使用。
- 代理 407 全线失败 + 换 IP 无效 + ~100ms 快速失败 = 认证/白名单问题，不是 IP 质量问题，别再烧 IP 换 IP。
- 「代理一直很稳定」的时期可能只是白名单在默默认证——排查代理问题先看控制台白名单和服务器出口 IP，别只盯着代码里的凭证。
