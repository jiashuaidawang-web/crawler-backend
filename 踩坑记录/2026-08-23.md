# 踩坑记录 2026-08-23

## 同花顺 L2 实时数据引擎 - tb1.0 协议逆向 + 帧头变长问题

### 问题现象

1. **引擎连接服务器成功但 Redis 无数据**：TCP 连接、登录、订阅都正常，但 tick 数据始终为 0
2. **JSON 解析不完整**：解析到的 JSON 是 `{"stockcode":"002384","value":"..."}` 而不是 `{"JiTu":[{"stockcode":"002384","value":"..."}]}`
3. **tb1.0 格式无法提取价格**：二进制数据检测到但无法解析出有用的价格信息

### 根因

#### 根因 1：帧头是变长的（影响：tick 数据全部丢失）

**现象**：解析器假设帧头固定 40 字节，payload 从偏移 40 开始。

**真实情况**：
- JSON 帧：payload 从偏移 **37** 开始（帧头 37 字节）
- itb3.0/tb1.0 帧：payload 从偏移 **40** 开始（帧头 40 字节）

**影响**：从偏移 40 开始提取 JSON 会丢失前 3 个字节 `{"Ji`，导致：
- JSON 被截断为 `iTu":[{"stockcode":...`
- `_extract_json` 找到的是内层 `{"stockcode":...}` 而不是外层 `{"JiTu":[...]}`
- `extract_ticks` 找不到 "JiTu" key，返回空列表

**修复**：添加 `_find_payload_offset()` 方法，通过查找已知标记（`{"`, `itb3.0`, `tb1.0` 等）来确定实际 payload 位置。

**文件**：`D:/stock/data/ths_l2_realtime.py` - `_parse_frame()` 方法

#### 根因 2：tb1.0 格式复杂（影响：价格提取不完整）

**现象**：tb1.0 二进制格式包含 UTF-16LE 编码的字符串和 4字节整数混合。

**结构发现**：
```
tb1.0 header (40 bytes):
  [0:6]   = "tb1.0\x00"
  [6:10]  = count (DWORD)
  [10:14] = reserved
  [14:18] = reserved
  [18:20] = struct_size (WORD)
  [20:22] = market (WORD)
  [22:26] = flags (DWORD)
  [26:30] = unknown1 (DWORD)
  [30:34] = timestamp1 (DWORD)
  [34:36] = unknown2 (WORD)
  [36:40] = timestamp2 (DWORD)

data_area (变长):
  - UTF-16LE 编码的股票代码（6位数字）
  - UTF-16LE 编码的价格字符串（含小数点）
  - UTF-16LE 编码的成交量字符串
  - 4字节小端整数（flags/volumes）
```

**已知价格样本**（来自 resp_063.bin）：
- 股票代码: "881270"
- 价格: 23864.20, 363.9, 1.5, 4.19
- 成交量: 23500, 2405

**注意**：23864.20 看起来不像正常股票价格，可能是某种汇总值或指数。

### 修复

1. **`_parse_frame()`**: 使用 `_find_payload_offset()` 动态确定 payload 起始位置
2. **`L2DataExtractor.parse_tb10()`**: 新增方法解析 tb1.0 格式
3. **`RedisWriter.add_tb10()`**: 新增方法写入 tb1.0 数据到 Redis
4. **`_process_frame()`**: 集成 tb10 数据提取和统计

### 关键排查经验

1. **变长协议要用标记定位**：不要假设固定偏移量，应该通过查找已知标记（Magic、JSON brace、ASCII 标记）来确定边界
2. **字节序很重要**：同花顺协议混合使用了小端序（DWORD/WORD）和 UTF-16LE 编码
3. **对比多个样本**：单个样本容易被误导，对比多个帧（resp_025/027/063）才能发现规律
