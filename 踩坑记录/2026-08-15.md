# 2026-08-15 监控踩坑：日志滚动导致 pipeline 状态误判 + pipeline 卡死

## 问题现象

实时监控 `logs/admin.log` 汇报编排器执行状态。监控启动后约 60 分钟一直报"🔇 admin 日志无新事件（停滞）"，给出错误结论"pipeline 卡在 STOCK_BY_BOARD（SQL bug 阻断），需要人工介入"。

实际上 **pipeline 一直在高速推进**，日志在 18:11 后滚动到了 `info.log`，`admin.log` 不再更新。误判持续了约 60 分钟 / ~60 次轮询。

## 根因

**监控设计缺陷（主因）：** 只盯住 `admin.log` 一个文件，没有检查 logs 目录是否有日志滚动/切分。

Java 项目常用 logback/log4j 按大小或时间滚动日志。本项目的实际布局：
- `admin.log`（1.2MB，18:11 后冻结）—— 编排器事件早期写这里
- `info.log`（12.6MB，持续更新到 23:17）—— 滚动后编排器+worker 事件都写这里
- `error.log`（4.7MB）—— 错误堆栈
- `worker.log`（3.4MB，18:11 冻结）

日志滚动后，编排器日志事件改写到 `info.log`，但监控还在读 `admin.log`，导致完全误判。

**真实 pipeline 状态（23:17）：** `date=08-14` 的 pipeline 在 22:33 被 force 重跑后快速推进到 BOARD_BASIC，然后卡在最后 1 个 PENDING 任务 ~31 分钟（编排器 dead task 卡死，需人工 forceResetDeadTasks）。

## 修复

监控策略修正：
1. **必须扫描整个 logs 目录**，检查所有活跃日志文件（`admin.log`/`info.log`/`error.log`/`worker.log`），不能只盯一个文件
2. 用 `ls -la logs/` 发现 `info.log` 时间戳最新 → 切到 `info.log` 监控
3. 轮询发现重复无变化时，改为 5 分钟心跳，避免刷屏

## 关键排查经验

> **监控日志文件前，先看 `ls -la logs/` 确认哪个文件在增长。** 日志滚动是最常见的"假停滞"原因。判断真正停滞的标准是：**所有**日志文件的时间戳都停止增长，而非某一个文件无新内容。
