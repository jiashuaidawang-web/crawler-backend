# 踩坑记录 2026-08-17

一键跑批接口 `POST /api/job/pipeline/daily` 返回 500、且服务启动后端口瞬时不可达的全过程。最终定位出**编排层 bug** + **预先存在的 logback 环境损坏**。

## 问题现象

- 触发接口：`POST /api/job/pipeline/daily`（date 缺省=今天 2026-08-17）。
- 返回 `{"status":500,"error":"Internal Server Error","path":"/api/job/pipeline/daily"}`，**error.log / info.log 里没有 500 的堆栈**。
- admin 进程（刚启动）8081 端口 `curl` 返回 HTTP 000 / 500 不稳。
- 表象像是"今天跑批没执行"。

## 排查路径

1. **先查服务存活**：`curl localhost:8081` → HTTP 000，admin 进程根本没起来（日志最后一条是当天 00:08:21 的 shutdown）。手动 `java -jar` 拉起。
2. **拉起后 500 无堆栈**：info.log 停在 20:57、error.log 停在昨天，500 的异常**没落盘**——这是第一个异常点。
3. **查 pipeline_run 表**：发现今天 `run_id=8, status=RUNNING, started_at=2026-08-16 15:00`——**跑批不是没执行，是昨天下午触发后卡死**。更关键：`pipeline_stage` 表里 run_id=8 **没有任何记录**（stage 行数=0）。
4. **读 `DailyPipelineOrchestrator.ensureRun`**：看到对 FAILED/ABORTED 的 run 会 `insertRun` 新建行，但表有 `uq_pipeline_run_date` 唯一约束 → 必然 `DuplicateKeyException` → 500。昨天 error.log 已有 `(run_date)=(2026-08-14) already exists` 佐证。
5. **500 堆栈为何消失**：`Exception in thread "http-nio-8081-exec-2" NoClassDefFoundError: ch/qos/logback/classic/spi/ThrowableProxy`——**logback 记异常对象时自身崩了**，堆栈被吞。这是预先存在的环境问题（2026-08-14 error.log 同错），与本次改动无关。

## 根因（按影响排序）

### Bug 1（阻断·真 bug）：`ensureRun` 违反唯一约束 → 重跑永久 500

`crawler-admin/.../pipeline/DailyPipelineOrchestrator.java:310-337`

```java
// FAILED/ABORTED → 新建一条 run(保留历史,不覆盖旧 run)
PipelineRun r = new PipelineRun();
r.setRunDate(date);
pipelineMapper.insertRun(r);   // ← 表有 uq_pipeline_run_date，每天只容一条，必然 DuplicateKeyException
```

- 表约束 `schema-pipeline.sql:14`：`CONSTRAINT uq_pipeline_run_date UNIQUE (run_date)`，设计是"同日只一条，重跑走 resume"。
- 代码意图"保留历史不覆盖"与约束矛盾 → 一旦某天 FAILED，后续所有 `daily` 调用都 500，**永久不可重跑**。
- mapper 里已写好 `insertRunIgnoreConflict`（带 `WHERE NOT EXISTS`）但从未使用——是死代码。

### Bug 2（阻断·真 bug）：卡住的 RUNNING run 永久阻断 `daily`

`DailyPipelineOrchestrator.java:313-314`

今天 run_id=8 就是实例：status=RUNNING 但 stage 行=0（`initStages` 没跑成功 or 建 run 后进程挂了）。`ensureRun` 看到 RUNNING → 返回 null → `run()` 直接 `return status()`，**什么都不做**。`resume()` 也救不了——`execute` 里 `persistStage` 是 UPDATE，行不存在则更新 0 行，白跑。

`PipelineMapper` 里写了 `abortStaleRuns`（把陈旧 RUNNING 标 ABORTED），但**整个项目没人调用它**——设计好了未接上的安全网。

### Bug 3（隐蔽·预先存在）：logback throwable-proxy 路径损坏 → 异常堆栈被吞

```
Exception in thread "http-nio-8081-exec-2" java.lang.NoClassDefFoundError: ch/qos/logback/classic/spi/ThrowableProxy
    at ch.qos.logback.classic.spi.LoggingEvent.<init>(LoggingEvent.java:143)
```

- **非本次引入**——2026-08-14 error.log 就有 `ClassNotFoundException: ch.qos.logback.classic.spi.ThrowableProxy`。
- jar 本身完整（SHA1 对、`ThrowableProxy.class` 5578 字节在 jar 内、`javap` 能反编译），是**类加载 / 初始化链**层面的环境损坏。
- 后果：任何 `log.error("...", e)` 传异常对象都会触发 → 日志框架自身崩 → 异常堆栈被吞、响应写不出去（500 无堆栈的元凶）。
- 仅影响"记异常堆栈"，`log.info` / 只传 message 的 `log.warn` 正常。

### 非阻塞但需知

- **跑批同步阻塞 HTTP 线程**：`await()` 每阶段最长 `awaitTimeoutMin`（默认 60min），17 阶段串行 = 一个 POST 可持有 Tomcat 线程数小时。调用方超时后服务端仍在跑，状态认知不一致。本地无 worker 时 STOCK_DAILY 就会卡满 60 分钟超时。
- **`STOCK_WEEKLY.taskTypes=List.of()`**：该阶段实际是同步 DB 聚合（`aggregateAllWeekly`，不产出 crawl_task），所以 taskTypes 为空**是正确的**——完成探测查不到任务 → pending=0 → 立即完成，符合实际。之前误判为 bug，已还原。

## 修复（已部署验证，crawler-admin v5）

### 代码修复

① **`ensureRun` 改用 `insertRunIgnoreConflict`，FAILED/ABORTED 原地 reset 重用**
`DailyPipelineOrchestrator.java`

```java
// FAILED/ABORTED → 原地 reset 重跑。表有 uq_pipeline_run_date,每天只能一条 run,
// 不能 insert 新行(会 DuplicateKeyException),只能在原 run 上重置。
if (resetIfExists) {
    pipelineMapper.resetStagesToPending(latest.getRunId());
    pipelineMapper.resetRunToRunning(latest.getRunId());
}
initStages(latest.getRunId());
return latest.getRunId();
```

- 首次跑用 `insertRunIgnoreConflict`（防并发插入冲突），insert 后统一按日期重查 runId。
- 验证：run_id=8 从 ABORTED 复用为 RUNNING，无 500。

② **启动时清理陈旧 RUNNING（`@PostConstruct`）**
`PipelineMapper` 新加：
```sql
UPDATE pipeline_run SET status='ABORTED', finished_at=now() WHERE status='RUNNING'
```
`DailyPipelineOrchestrator.abortStaleRunsOnStartup()`：启动时调用，DB 不通只 `log.warn` 不阻断启动。
- 验证：启动日志 `已将 2 条陈旧 RUNNING run 标为 ABORTED`。

③ **`execute()` 开头 stage 行缺失兜底**
```java
if (stageRows.isEmpty()) {
    log.warn("[pipeline] date={} runId={} 无 stage 行,兜底补建", date, runId);
    initStages(runId);
    stageRows = pipelineMapper.selectStages(runId);
}
```
- 验证：run_id=8 重建出 17 行 stage（原来 0 行）。

④ **全局异常兜底 + 绕过 logback 损坏路径**
新文件 `controller/GlobalExceptionHandler.java`：`@RestControllerAdvice` 捕获所有 `Exception`，**只记消息不传异常对象**（`log.error("[未捕获异常] {}: {}", e.getClass().getSimpleName(), e.getMessage())`），避免触发 `ThrowableProxy`，返回统一 JSON。
- 验证：500 现在带消息落盘、POST 返回 200/明确错误。

### 线上修复

无需DDL / 数据迁移。代码修复重启即可。

## 关键排查经验

1. **"没执行"≠"没跑过"**：先查 `pipeline_run` 表 status，RUNNING 但无 stage 行 = 卡死，不是没触发。
2. **500 无堆栈 ≠ 没有异常**：先怀疑日志框架本身是否健康（看 error.log 有没有 `LoggingEvent` / `ThrowableProxy` 类错误）。
3. **代码意图 vs 表约束矛盾**：`insertRun` 注释写"支持同日多次跑批"，但表是 `UNIQUE(run_date)`——读代码时对照 schema 能直接发现。
4. **启动硬失败要留退路**：`@PostConstruct` 里调 DB 必须 try-catch，否则一次 DB 抖动就让服务起不来。
