# 2026-09-27 踩坑记录

## 问题1：A股全历史 stock_daily 回填方案 — push2 clist API 不支持历史日期

### 现象
- 对缺失的历史交易日（如 1991-01-01）创建 STOCK_DAILY 任务后，Worker 执行时东财 API 返回的是**当前市场快照**而非历史数据
- 导致 stock_daily 表中出现 trade_date=1991-01-01 但数据是当前行情的脏数据
- 日志显示探测 total=5561（当前全市场股票数），而不是历史日期的真实数据

### 根因
东财 push2 clist API（`push2.eastmoney.com/api/qt/clist/get`）是一个**市场快照接口**，不接受 tradeDate 参数，始终返回当前交易日数据。STOCK_DAILY 的 tradeDate 仅用于种子 params 传给 Worker 标记 trade_date 字段，API 本身不感知日期。

### 修复
1. 停止回填进程，清理了 200 个错误 PENDING 任务
2. 重新设计：历史回填必须使用 STOCK_DAILY_HISTORY（push2his kline 逐券拿全历史），不能用 STOCK_DAILY（clist 快照）

### 关键排查经验
- **东财 clist API = 当前快照，不含历史**。历史数据必须走 push2his kline（逐券）
- 回填历史数据前，先确认数据源 API 是否支持目标日期，避免写入脏数据
- 测试时先用 gap-only 模式验证，但也要验证 API 返回的数据是否正确（不只是看 total>0）

## 问题2：ClickHouse 无法启动 — stock_daily 表分区损坏

### 现象
- ClickHouse Docker容器无限重启，exit code 70
- 日志显示大量 `while loading part XXXX: Code: 27. DB::ParsingException: Cannot parse input: expected 'columns format version: 1\n' at end of stream`
- 容器状态：`Restarting (70)`，重启23次

### 根因
1. **权限问题**（次要）：数据目录权限被破坏，clickhouse用户无法创建 `preprocessed_configs` 目录
2. **分区文件损坏**（主要）：`crawler.stock_daily` 表的 ReplacingMergeTree 存储中，3652个数据分区（part）的 `columns.txt` 文件为空或截断
   - 损坏分区覆盖 2010~2023 年数据
   - 错误信息：`expected 'columns format version: 1\n' at end of stream` — 分区元数据文件不完整

### 排查过程
1. 先怀疑权限问题：以clickhouse用户启动时报 `Permission denied ["./preprocessed_configs"]`
2. `chown -R clickhouse:clickhouse /var/lib/clickhouse` 修复权限
3. 以root启动能走更远（保存preprocessed_configs成功），但仍exit 70
4. 查看错误日志发现真正的加载分区失败
5. 用bash启动server并查看 `/var/log/clickhouse-server/clickhouse-server.err.log` 找到详细错误

### 修复
1. 修复数据目录权限：`chown -R clickhouse:clickhouse /var/lib/clickhouse`
2. 识别坏分区：`columns.txt` 文件不存在或为空
3. 批量移到备份目录：
   ```bash
   mkdir -p /var/lib/clickhouse/backup_broken_parts
   cd /var/lib/clickhouse/store/493/49346d14-eb5a-495a-97d0-07e2fe9078b9
   for part in *; do
     if [ -d "$part" ]; then
       cols="$part/columns.txt"
       if [ ! -f "$cols" ] || [ ! -s "$cols" ]; then
         mv "$part" /var/lib/clickhouse/backup_broken_parts/
       fi
     fi
   done
   ```
4. 移走3653个坏分区，保留50751个正常分区
5. 重新启动CK容器，正常运行

### 数据完整性验证
- stock_daily: 20,097,240行，日期范围 1990-12-19 ~ 2026-09-26，8,803个不同交易日 ✅
- stock_trade_calendar: 13,067条记录 ✅
- 3个Worker恢复正常运行，持续写入数据

### 关键排查经验
- **Git bash (mingw64) 路径转换会破坏Docker参数**：`/etc/clickhouse-server/config.xml` 被转成 `D:/Development/Tool/Git/Git/etc/...`。涉及Docker挂载路径时用PowerShell或cmd
- **ClickHouse exit code 70 = 启动失败**，看 `/var/log/clickhouse-server/clickhouse-server.err.log` 找具体原因
- **ReplacingMergeTree 分区损坏**时，CK无法启动。需要手动移除坏分区（empty/truncated columns.txt）
- 坏分区特征：`columns.txt` 文件不存在或0字节

## 问题3：无守卫调度在周末写入快照脏数据（7 天 × 5,560 行 + 北向垃圾行）

### 现象
- stock_daily 存在 7 个周末日期（2026-09-05/06、09-12/13、09-19/20、09-26），每天约 5,560 行，内容全是上一交易日的快照
- northbound_flow 存在 09-26 行，字段错位（status_flag=8400000 = 4200000+4200000，解析错乱）

### 根因
1. 15:30 自动日批调度上线（约 08-20）时**没有交易日守卫**——`git show HEAD:DailyScheduler.java` 中 `checkTradingDay` 出现 0 次，`TradingDayChecker.java` 是 9/26 晚 407 修复时新增的文件（不在 HEAD）
2. clist 是当前快照 API，周末返回上一交易日数据，trade_date 由任务参数打戳 → 周末跑批 = 拿周四数据标周六日期
3. 09-25（中秋）反而无脏数据：当天 admin 未运行，纯属侥幸

### 修复（已执行）
- `ALTER TABLE crawler.stock_daily DELETE WHERE trade_date IN ('2026-09-05','2026-09-06','2026-09-12','2026-09-13','2026-09-19','2026-09-20','2026-09-26')`，删 38,921 行，mutation 完成后验证 0 残留
- 删除 northbound_flow 09-26 垃圾行
- **守卫已实测生效**：2026-09-27 18:00 日志 `date=2026-09-27 klines.size()=0, isTradingDay=false` → `自动调度跳过(非交易日或接口不可信)`；周日龙虎榜被正确拦截
- push2his kline 对非交易日确实返回空 klines（09-25/26/27 三日实测），守卫的 API 假设正确

### 关键排查经验
- **快照类 API（clist/kamt.rtmin）+ 定时调度 = 必须有交易日守卫**，否则每个周末都会写脏数据
- 调度守卫类 bug 排查第一步：`git show HEAD:<file>` 确认生产代码到底有没有这段逻辑，别只看工作区

## 问题4：交易日历全部来自周末推断 → 600 个幻影交易日

### 现象
- stock_trade_calendar 13,067 行**全部** src_detail=weekend_inference_fallback（akshare-bridge 从未成功过）
- 所有工作日 is_trading=1，法定假日全是幻影交易日，共 **600 个**
- 早上差距检测报的"601 个缺失交易日"里 599 个是幻影——真实缺口只有 2 天

### 根因
- akshare-bridge 拉日历失败，降级到周末推断（周末=非交易、工作日=交易），推断逻辑不知道法定假日

### 修复（已执行）
- 权威日历改用**指数 K 线日期**：上证指数(secid=1.000001) 8,733 天 + 深证成指(0.399001) 8,686 天，**并集 8,778 天**
- 直连 push2his 大范围请求被掐（exit 52/56，37 个年份分块全失败）→ 走青果代理按年分块拉取，一 IP 一次跑完（`scripts/backfill/fetch_index_kline2.sh`）
- 重建 stock_trade_calendar：新表写好 → `RENAME TABLE` 原子换表，is_trading 按并集，src_detail=sse_szse_index_kline_union_20260927；旧表保留为 `stock_trade_calendar_old_20260927`
- 交叉验证：与库内另一张 trade_calendar（2024-2026）比对，662/667 一致，5 个分歧日全部是并集对、trade_calendar 错（2024-02-09 除夕、2025-06-02 端午、2026-01-02 元旦、2026-02-16 春节均误标交易日；2026-02-24 误标非交易日——trade_calendar 自身存量错误，本次未修）

### 意外发现（数据史实）
- **深交所 1991-04 ~ 1993-01 有独立交易日程**：45 个深市独有交易日（周六也开市），上证同期不交易
- 1991-01 ~ 1991-03 还有 12 个周六有老五股（000002/000004/000005.SZ）数据——深证成指 1991-04-03 才发布，之前是柜台交易期
- 18 个"沪深成指都没有"的早期日期（含 1993-05-01/02 五一 23 只深市股成组数据）判定为源数据保留，不删

### 关键排查经验
- **"上证指数没交易 ≠ 全市场没交易"**——沪深早期日程独立，A 股日历要用两市并集
- 指数 K 线日期是实证权威（市场真交易过才有 bar），比任何推断/官方表都可靠
- CK 语法坑：`FROM t FINAL WHERE ...` 可以，`FROM t FINAL c WHERE`（别名放 FINAL 后）直接语法错误

## 问题5：kamt.rtmin 北向接口 date 参数被忽略，历史日期不可补

### 现象
- NORTHBOUND_FLOW|2026-09-23 / 09-24 两个任务 PENDING（9/23、9/24 15:4x 创建，恰逢 407 风暴 + CK 崩溃没跑成）
- 若直接重跑会写入脏数据

### 根因（实测实锤）
- curl 实测 date=20260922 / 20260923 / 20260924 **返回完全相同的数据**（9:30 都是 `0.00,5200000.00,...`），且与 09-22 当天实时写入 CK 的真值（buy=4200000）不符
- kamt.rtmin 是实时分钟接口，date 参数是摆设，始终返回最新会话数据

### 修复（已执行）
- 2 个任务标记 FAILED + error_msg 注明"API 不支持历史日期，勿重跑"（保留审计记录）
- 09-22 任务当天跑的（数据有效保留）；09-26 周六跑的（垃圾行已删）

### 关键排查经验
- **补历史数据前先实测 API 是否真支持日期参数**——返回 200 + 有数据 ≠ 返回了那天的数据，要拿已知真值对照验证
- 与问题1（clist 不支持历史）同属一类：东财实时/快照接口的日期参数普遍不可信

## 问题7：CK Code 252 — 表级 max_parts_in_total=100k 被回填插入模式打穿，任务批量 FAILED

### 现象
- 22:18 起任务零完成（卡死 35 分钟），FAILED 从 1 暴涨到 495+
- 错误：`Code: 252. DB::Exception: Too many parts (100000) in all partitions in total in table 'crawler.stock_daily'`
- worker 全部存活，CK 无崩溃——纯写入被拒

### 根因
- **回填插入模式对 CK 是病态的**：每个任务一次 batch insert 横跨 ~430 个月分区（1991-2026 每月一个 part），3 worker 持续插入
- merge 跟不上（当时仅 3 个并发 merge），active parts 累积到表级上限 100,000，CK 拒绝一切写入
- 热门月份分区（200503/199704 等，全市场股票都有数据）积了 500+ part；每分区限制（delay 1000/throw 3000）没触发，卡的是**表级总限**

### 修复（已执行，22:50）
1. `ALTER TABLE crawler.stock_daily MODIFY SETTING max_parts_in_total = 300000`（表级设置即时生效，**无需重启**）
2. 重置 556 个 FAILED/RETRY → PENDING
3. 预防下一队列：`ALTER TABLE crawler.stock_kline_minute MODIFY SETTING parts_to_delay_insert = 3000, parts_to_throw_insert = 10000`（4,866 个分时任务全写 202609 单分区，会撞每分区 3000 上限）
4. 22:53 验证恢复：任务正常完成，merge 并发 3→22 追赶，parts 105k（余量充足）

### 后续
- 排干后 merge 会自动收敛 part 数，次日应复查 active_parts 是否降到千级
- **未来回填的正确姿势**：DedupWriter 应按分区聚合写入（攒批后按月分区 insert），或用 INSERT SELECT 从 staging 表搬运，避免一次 insert 横跨几百分区

### 关键排查经验
- **Code 252 看清楚是哪个限制**：报错文本带 "in all partitions in total" = 表级 max_parts_in_total；带 "in partition" = 每分区 parts_to_throw_insert
- 表级/分区级 part 设置都可用 `ALTER TABLE ... MODIFY SETTING` 在线调整，不用重启
- 排干速度 480-615/小时的波动 = parts_to_delay_insert 的节流在生效（热分区插入被强制 sleep），这是 CK 在自我保护，别当成故障
