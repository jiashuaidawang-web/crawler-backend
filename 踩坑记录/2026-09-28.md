## 问题1：Docker Desktop 引擎第三次 wedge（04:17 发现），CK/PG 全停

### 现象

- 04:17 例行检查时 `docker ps`、`docker version` 全部返回 `500 Internal Server Error ... dockerDesktopLinuxEngine`——不是容器挂，是 **Linux 引擎 API 整个无响应**
- Docker Desktop 进程全活着、`wsl --list` 显示 docker-desktop 发行版 Running——**进程在、VM 标记在、引擎死**
- 回填流水线全停：worker 连不上 PG/CK，在途任务批量 `Read timed out` 失败

### 根因

### 修复（已执行，04:20）

```
taskkill //F //IM "Docker Desktop.exe"
taskkill //F //IM "com.docker.backend.exe"

# 重新启动 Docker Desktop，等 ~60s 引擎恢复
```

### 关键排查经验

- `docker version` 都 500 = 引擎级故障，重启 Docker Desktop 全家是唯一解，等是等不好的
- **判断容器是否 crash loop 看 `docker inspect --format '{{.RestartCount}} {{.State.StartedAt}}'`，别看 docker logs 的重复块**（那是跨重启的历史日志）

## 问题2：CK 内存死亡螺旋（305k parts 元数据 ~32GB 底座），一天内反复假死

### 现象

- 05:53：最后成功停在 05:41，CK 8123 无响应（exit 52），但容器 Up、无 OOM、无重启
- clickhouse-server 占 **46.18/49.02 GiB（94%）**；err.log 栈显示新 HTTP 连接的 `ReadBufferFromPocoSocket` 分配失败——server 活着但无法接受任何连接
- **273k+ parts 却 0 个 merge 在跑**：内存耗尽饿死 merge 调度，parts 只进不出
- 重启后 10 分钟内存又冲回 46GB+；`SYSTEM DROP MARK CACHE` 无效（大头不是缓存）
- OvercommitTracker 杀查询：`Memory limit (total) exceeded: would use 44.23 GiB, maximum: 44.11 GiB`

### 根因（按影响排序）

1. **parts 元数据内存底座**：305k active parts ≈ 32.8GB 常驻（重启后实测基线），清缓存/停活动都不降
2. **插入与 merge 抢内存**：3 worker 持续插入（每任务 ~430 分区各 1 part）+ merge 工作集叠加 → 触顶 → 杀 merge → parts 继续涨 → 恶性循环
3. **单个巨型 merge 也能致死**：`background_pool_size=1` 只限并发数不限单 merge 内存——201711 分区 4,551 parts 的 merge 自己就吃 10GB+（merge 内部多线程，CPU 500%）
4. **胜负账**：OPTIMIZE 2.5min/分区 ≈ -17k parts/h；worker 插入 150/h × 430 ≈ **+65k parts/h → 边插入边优化必输**

### 失败的尝试（别再走这些弯路）

| 尝试 | 结果 |
|------|------|
| 清缓存（DROP MARK/UNCOMPRESSED/DNS CACHE） | ❌ 无效——parts 元数据不是缓存 |
| 重启后抢 `SYSTEM STOP MERGES` | ❌ 赢不了——元数据加载完的瞬间调度器就开跑，STOP 只挡新的挡不住在途的 |
| `background_pool_size=1` 配置 | ❌ 单独无效——单 merge 多线程照样吃爆；且触发启动自检崩溃（见问题3附） |
| 零插入下让调度器自消化 | ❌ 16 并发巨型 merge 自己就把内存打爆 |
| `SYSTEM STOP MERGES` 后跑 OPTIMIZE | ❌ STOP 连 OPTIMIZE 一起掐死（Code 236 Cancelled） |

### 真正的修复：磁盘级隔离 + 整表重建（见问题3）

## 问题3：stock_daily 月分区设计缺陷——430 分区 part 爆炸（根治）

### 根因（设计层面）

36 年日线数据 `PARTITION BY toYYYYMM(trade_date)` = **430 个月分区**，每分区才 ~110k 行（20-50MB）。每个全历史回填任务（push2his lmt=50000）一次插入横跨全部 430 分区各造 1 个 part → 5,561 任务 = 240 万个 part 输入，merge 永远追不上 → 问题2 的死亡螺旋。

**年分区才是这个数据量的正确粒度**（37 分区 × ~50 万行/分区），每次插入只造 37 个 part，压力降 11.6 倍。

### 修复：五步重建（07:20-09:20，全程数据零丢失）

1. **磁盘级隔离**（server 停机，helper 容器挂卷操作）：
   ```
   # 表数据目录（Atomic 引擎，从 metadata/crawler/stock_daily.sql 的 UUID 定位）
   T=/data/store/493/49346d14-eb5a-495a-97d0-07e2fe9078b9
   find $T -maxdepth 1 -type d -name '[0-9]*_*' -print0 | xargs -0 -n 2000 mv -t $T/detached/
   # 70.5 万 part 目录全部移入 detached/ → server 以空表启动 → 内存地板 46GB→321MB
   ```
   **这是整个修复的关键一步**：detached/ 的 parts 不加载不 merge，server 启动 5 秒（原来 2 分钟）、内存 0.6%——巨型 merge 从根上不存在，所有后续操作都在安全余量内进行。

2. **建年分区新表**（同 schema 同引擎，`PARTITION BY toYear(trade_date)`）

3. **逐月 ATTACH→INSERT SELECT→DETACH 循环**（430 个月，每月临时挂载→拷贝→卸回 detached/，内存峰值 7GB）：
   - 耗时 80 分钟，**17,914,620 行，`new_total = sum_cycles = uniq_keys` 三方核对全等**——每行恰好一次零重复
   - 坑：CK 年函数是 **`toYear()` 不是 `toYYYY`**（第一版脚本因此空转，430 个月全报 Unknown function）
   - 坑：inactive parts（已被 merge 取代待清理的）也一并拷入——无害，ReplacingMergeTree 按排序键去重语义不变

4. **原子切换**：`RENAME TABLE ... TO ..._old_monthly, ..._new TO ...` + `DROP` 旧表（释放全部 70.5 万 parts）

5. **恢复配置重启放行**：10 秒启动（原来 2 分钟）、74 parts（原来 30.5 万）、内存 2.85GB。放行 571 个扣住的任务后 **~1,550 任务/h**（死亡螺旋期 65/h 的 24 倍），20 分钟排干。

### 修复期间的两个运维坑

- **暂停 worker 消费的可靠手段只有把任务置为 FAILED/DEAD**：
  - ❌ `RETRY + next_retry_at=未来时间` 无效——**worker 认领查询不理会 next_retry_at**，RETRY 池被持续吃掉，10 分钟 56 个任务烧成 FAILED/DEAD。这是 worker 的待修 bug。
  - ✅ FAILED/DEAD 是 worker 永不认领的状态（全天验证）
- **`docker restart` 对 wedge 状态的 CK = 硬杀**：在途 merge 写一半被杀 → 可能产生 0 字节 part（昨天的 Code 231 模式）。今天运气好没产生。**正确姿势：先 `docker stop`（给 10 秒优雅退出）再操作**

### 终验结果（09:50 全部通过）

| 验证项 | 结果 |
|--------|------|
| 缺口查询（SSE∪SZSE 指数日历 union vs stock_daily） | **恰好 2 个缺失：1991-04-27、1991-08-10**（1991 深市周六场，东财 kline 无数据的数字前时代残差，与预测完全一致） |
| 幸存者复核（PG crawl_stock_backfill_status vs CK 逐股天数，deficit>50 判真丢） | **REAL_LOSS=0**，5,561 只全部完好 |

### 附：background_pool_size 调小的连锁自检（如果真要调）

`background_pool_size=1` 会触发启动自检崩溃（exit 70，每分钟 crash loop 一次），必须同时把 merge_tree 段这三项压到 0：
```xml
<background_pool_size>1</background_pool_size>
<merge_tree>
    <number_of_free_entries_in_pool_to_execute_mutation>0</number_of_free_entries_in_pool_to_execute_mutation>
    <number_of_free_entries_in_pool_to_lower_max_size_of_merge>0</number_of_free_entries_in_pool_to_lower_max_size_of_merge>
    <number_of_free_entries_in_pool_to_execute_optimize_entire_partition>0</number_of_free_entries_in_pool_to_execute_optimize_entire_partition>
</merge_tree>
```
（这族设置要 ≤ background_pool_size × background_merges_mutations_concurrency_ratio，默认 20/8/25 都 > 1×2=2。错误信息会逐个报名字，改一项崩一项，三项全改才能启动。）

### 关键排查经验

- **几十万 parts 的表在 49GB 主机上就是定时炸弹**：parts 数 × ~100KB ≈ 常驻内存。`max_parts_in_total` 调大只是把 Code 252 换成内存死亡螺旋
- **server 停机时直接 mv parts 到 detached/ 是降内存地板的终极大招**——比任何在线手段（STOP MERGES/OPTIMIZE/清缓存）都彻底，且数据不丢（ATTACH 随时取回）
- **分区粒度按"每次插入会命中多少分区"设计**，不只是按查询模式——批量回填场景月分区 430 个 = part 爆炸
- 容器"Up 但 8123 无响应 + err.log 有 HTTPServerRequest 分配失败栈" = server 级内存耗尽
- 判断 merge 是否在干活：`system.merges` 计数 + 容器 CPU%；parts 涨 + merges=0 = 调度器已饿死
- **空 error_msg 的批量 FAILED = CK 不可达时期的签名**（worker 异常路径没捕获消息），恢复后统一重置即可
- 僵尸 CLAIMED 判定：`started_at` 远早于最近成功时间且无进展

## 问题6：回填工程化中的机制确认（避免下次重新踩）

- **crawl_task 认领顺序 `ORDER BY priority DESC`**：数字大先跑。想插队（冒烟测试）用 9；想让大批量任务不挡别的队列用小数字（龙虎榜主表=5、资金流=4、席位明细=3）
- **insertInChunks 无任何去重逻辑**（DedupWriter.java:1311，纯 20 行/批插入）——"去重"完全靠 ReplacingMergeTree 后台按 _ver 合并。重叠回填会产生临时重复行（main_fund_flow 09-18 出现两条不同值，fflow 的 _ver 更新，合并后权威值胜出）。设计如此，不是 bug
- **FFLOW 历史回填的分区压力可控**：main_fund_flow 虽是月分区，但 fflow 窗口只跨 6 个月分区、每任务每分区仅 ~1 个 20 行小 part——与 stock_daily 灾难场景（430 分区）完全不同量级
- **worker 停机重启成本极低**：PENDING 任务原地保留，僵尸 CLAIMED 统一 UPDATE 重置即可（本次 36 个）。改完代码直接 taskkill → mvn package → 重启，不用等队列排干
- **构建工具**：mvn 不在 PATH，用 IDEA 内置 `D:/Development/Tool/IDEA/IDEA_202602/APP/IntelliJ IDEA 2026.1.2/plugins/maven/lib/maven3/bin/mvn.cmd` + JAVA_HOME=jdk-21.0.11
- **大批量播种任务别用 bash 循环**：逐行 `echo | grep -qx` 每行 spawn 子进程，Windows/MSYS 下 ~18 行/秒，24.6 万行要 4 小时。正确姿势：CK 导出 TSV → `docker cp` 进容器 → PG 临时表 `\copy` + `INSERT...SELECT`（字符串拼接全在 SQL 里），**10 秒完成**（seed_dt_detail_hist.sh 已按此重写）

## 问题7：main_fund_flow 历史遗留脏数据（② 验证时发现并清除）

### 现象
② fflow 回填完成后验证：stock 侧 834,919 行、10,766 个 ts_code（预期 5,561）、最早 2011-07-22（预期 2026-04-03）；9 月每个交易日 ~5,200 只股票出现**两条值不一致的行**。

### 根因（按写入事件定位，update_date 直方图是关键证据）
1. **2026-08-22 10:05 同花顺(THS)一次性导入实验**（src_detail=`ths_stock_fund`/`ths_fund_flow`，data_source=0）：
   - 5,205 行**裸码个股**（无 .SH/.SZ 后缀）→ 与后缀码永不同键，ReplacingMergeTree 永远无法去重，且数值是同花顺口径（平安银行 08-21: +8890 万 vs 东财真实 -9497 万）

   - 387 行 obj_type='concept'（同花顺概念资金流）→ 独立 obj_type 无污染，**保留未删**
2. **2026-09-22 13:53–16:12 CK 容器恢复当天的"补历史"尝试**：给 09-01→09-22 每个日期跑 MAIN_FUND_STOCK/BOARD clist 任务——但 **clist 快照接口不认日期参数，永远返回当天当前值**，结果 09-01→09-21 全被盖上 09-22 当天值（83,182 股票行 + 15,448 板块行）。与池表周末脏数据同一类坑：**快照型 API 不能用于补历史**

### 修复（已执行，CK ALTER DELETE，共删 103,925 行）

## 问题8：crawl_task 时间戳混合时区 → 按时间过滤全是坑

### 现象
监控 ④ 回填速率时，`updated_at > now() - interval '30 minutes'` 返回 7 个（看似速率暴跌到 7/30min），但 worker 日志同时段有上千次成功；`ORDER BY updated_at DESC` 看到的"最新任务"全是带 timeout 错误的旧任务。一度误判为代理集体失效。

### 根因
- **PG 容器时区 = UTC**（`SELECT now()` → `08:10+00`），本机/Java = UTC+8
- crawl_task 的 `started_at`/`updated_at` 混合两种写入：**Java JDBC 写入的值是本地时间 16:06**（pgjdbc 按 JVM 默认时区序列化 naive timestamp），**SQL 里 `now()` 写入的值是 UTC 08:06**
- 后果①：同一时刻两种戳相差 8 小时，`ORDER BY updated_at DESC` 永远把本地时间戳的行排最前（实际是旧任务）
- 后果②：`updated_at > now()-interval` 的过滤条件对本地时间戳行恒真/对 UTC 行恒假，统计完全失真

### 修复
不改代码（改需统一 JDBC session 时区，影响面大，另议）。**运维侧规避**：
- 测速率只用**纯状态计数**：隔 N 分钟 `SELECT count(*) ... WHERE status='SUCCESS'` 相减，不碰时间戳
- 需要按时间查询时用**显式日期字符串**（`updated_at >= '2026-09-28 15:45:00'`）并意识到结果可能缺 UTC 戳的行

### 关键排查经验
- openGauss 容器内 `now()` 是 UTC；Java 写库是本地时间——**凡 timestamp without time zone 列 + 混合写入方，按时间过滤前先 `SELECT now()` 对表**
- 真实速率 138 个/分钟（7 worker），之前"73/min"与"暴跌"两个数字都不可信；按状态计数为准
