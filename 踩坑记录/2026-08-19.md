# 2026-08-19 踩坑记录

## 1. ClickHouse 连接池连接被判死导致聚合报错(SQLSTATE(08000) ErrorCode(210))

### 问题现象

admin 日批编排触发后报错:
```
HikariPool-1 - Connection ... marked as broken because of SQLSTATE(08000), ErrorCode(210)
java.sql.BatchUpdateException: The target server failed to respond
```
调用链:`PipelineController.daily` → `DailyPipelineOrchestrator.run` → `SeedGenerator.seedWeeklyResult` → `StockWeeklyAggregator.aggregateWeeklyForStock` → `weekAlreadyExists` → `selectExistingTradeDates`(CK 查询)。

紧接着日志出现 `HikariPool-1 connection adder ... Connection TTL: 0 ms`,确认是连接被服务端/网络掐断后 HikariCP 补连接。

### 根因

`DataSourceConfig.chDataSource`(`crawler-persistence/src/main/java/com/dunwugudao/crawler/persistence/config/DataSourceConfig.java:86-99`)的 ClickHouse 连接池只设了:
```java
cfg.setMaximumPoolSize(5);
cfg.setConnectionTimeout(10000);
```
**没设 `keepaliveTime` / `maxLifetime` / `connectionTestQuery`**。

- ClickHouse 服务端 `keep_alive_timeout` 默认 30s 会主动掐断空闲 TCP,机房 LB/防火墙也会判死空闲连接。
- 凌晨 5 点跑日批聚合,池里连接是之前建好闲置数分钟的「僵尸连接」,HikariCP 不知道已坏,一用就触发 ErrorCode(210)。
- 报错发生在聚合循环的**第 2 次查询**(第 1 次 `selectByTsCode` 已成功),所以是连接中途被判死。

### 修复

`DataSourceConfig.chDataSource` 加三项:
```java
cfg.setKeepaliveTime(60000);          // 1min 发 HTTP keepalive,防 LB/防火墙判死
cfg.setMaxLifetime(1800000);          // 30min,让连接在被判死之前主动退役
cfg.setConnectionTestQuery("SELECT 1"); // 借用时校验,兜底踢掉僵尸连接
```
**核心是 `keepaliveTime=60000`**,`maxLifetime` 是兜底。

状态:已执行,待重启 admin 生效。

### 关键排查经验

> ClickHouse JDBC 连接池必须开 keepaliveTime,否则空闲连接会被服务端 keep_alive_timeout(默认 30s)掐断,报 ErrorCode(210) "target server failed to respond"。看到 `connection adder ... Connection TTL: 0 ms` 就是 HikariCP 在补被判死的连接。

## 2. 日批编排页面校验口径误报失败(历史存量行数干扰本次 run 校验)

### 问题现象

日批编排页面阶段 1~9 显示 `有历史数据 N 行(非本次 run 产出),数据量正常`,但实际是 DONE;部分阶段被误报 FAILED。用户反馈"没有全部成功"。

### 根因

`DailyPipelineOrchestrator.recomputeStageValidation`(`crawler-admin/.../pipeline/DailyPipelineOrchestrator.java:219-251`)实时查 CK 行数当 `actual`,但 `TotalCountValidator.countActualByStage` 统计的是**表内全量(含历史存量)**,不区分"本次 run 写入"和"历史数据"。

阶段 1~9 的 `expected` 是本次 seed 探测值(如 5551),`actual` 是库里历史总量(如 5651),校验逻辑拿历史总量跟本次期望值比,极易误报。

### 修复

- `TotalCountValidator` 的 `countActualByStage` / `countDupGroups` / `countActual` / `countDupGroups` 新增 `onlyCurrentRun` 参数;true 时加 `create_date = ?` 过滤,只统计本次 run 产出。
- `recomputeStageValidation` 改调 `onlyCurrentRun=true`。

**前提:** 所有 CK 表都有 `create_date` 列(已验证 11 个 mapper XML),worker 写入时 `create_date = 当天`,所以按 `create_date = runDate` 过滤就是本次 run 产出。

状态:已执行,编译通过。

### 未修复(留 TODO)

写库校验路径(`executeStage` → `TotalCountValidator.validate`)仍用旧口径(统计全量)。所以**页面显示 DONE,但 pipeline_stage 表里存的 status 可能是 FAILED**。页面是对的,存储状态可能不一致。

分两步走:先修页面运营面(本次),下个 run 验证后再改写库校验口径(需给 `ValidateContext` 加字段或改 `validate` 默认行为)。

### 关键排查经验

> 校验 CK 行数时要区分"本次 run 写入"和"历史存量",否则历史数据会干扰校验。用 `create_date = runDate` 过滤是最简单口径(前提是 worker 写入时可靠写 create_date)。
